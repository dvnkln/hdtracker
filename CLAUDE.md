# hdtracker – Projektregeln

Self-hosted Media-Tracker, Single-User, Deployment per Docker Compose.

## Zusammenarbeit

- Antworten auf Deutsch; jede Änderung in 1–2 Sätzen ohne Fachjargon erklären.
- In kleinen Schritten arbeiten, vor größeren Aufgaben zuerst einen Plan vorlegen.
- Nach jedem MVP-Punkt stoppen und erklären, wie man testet.
- **Seit v0.1.0 veröffentlicht:** Datenbank-Änderungen nur noch über neue Migrationen (`npm run db:generate`), die bestehende Daten erhalten – nie alte Migrationen ändern oder löschen, kein „Volume neu anlegen“ mehr. Alle bis v0.1.0 sind in `drizzle/0000_init.sql` zusammengefasst.

## Stack

SvelteKit (adapter-node, Svelte 5 Runes), TypeScript, Drizzle ORM, better-sqlite3, Tailwind v4. Mobile-first.

- `better-sqlite3` bleibt auf v12 (v13 hat keine Prebuilt-Binaries mehr → bräuchte Compiler).
- SvelteKit bleibt vorerst auf 2.x: Version 3 erschien am 01.10.2026 und brachte beim Probelauf am 03.10.2026 288 Typfehler (Typen wie `Handle`/`SubmitFunction` liegen woanders, `tsconfig.json` muss `$app/tsconfig` erweitern, `config.typescript` entfällt); TypeScript 7 wird von SvelteKit 3 und svelte-check noch nicht unterstützt. Merkposten: nach den ersten Korrekturversionen mit `npx sv migrate` in einer Kopie neu versuchen. Bis dahin hebt `overrides` in `package.json` den von SvelteKit mitgebrachten Baustein `cookie` auf 0.7.x (Sicherheitshinweis zu < 0.7.0) – beim Wechsel auf SvelteKit 3 wieder entfernen. Vor Abhängigkeits-Updates: Vorher/Nachher-Screenshots der Hauptseiten vergleichen (`magick compare`), Cookie-Wege (Anmelden, Abmelden, Theme, kaputte Cookies) und einen Durchlauf auf leerer Installation prüfen.
- Docker-Image für amd64 + arm64: Die App wird nur einmal gebaut, auf der Architektur des Build-Rechners (`FROM --platform=$BUILDPLATFORM … AS build`), weil das Ergebnis überall gleich ist und der emulierte arm64-Bau langsam war und schon abgestürzt ist (Abbruchcode 132 beim Release 0.5.1). Je Architektur läuft nur `npm ci --omit=dev` (Stufe `deps`, bringt das passende better-sqlite3-Binary). Was zur Laufzeit ein natives Modul braucht, muss deshalb unter `dependencies` stehen. Kein Build-Cache in der Release-Action (Tags können den Cache anderer Tags nicht lesen).
- Server-Code liegt unter `src/lib/server/` (nie im Browser-Bundle).
- DB wird lazy über `getDb()` geöffnet; Migrationen laufen automatisch beim Start (`src/hooks.server.ts`).
- Code, URLs und DB-Werte auf Englisch (`/movies`, `/series`, `/anime`, `/games`; Kategorie-Keys ebenso).
- Oberfläche zweisprachig (Deutsch/Englisch): **alle** sichtbaren Texte in `src/lib/i18n/de.ts` + `en.ts` (gleiche Struktur, TypeScript prüft das). Im Browser `m.xyz` aus `$lib/i18n/index.svelte`, auf dem Server `serverMessages()`. Server liefert Werte (Minuten, ISO-Datum), formatiert wird in der Oberfläche.
- Start über `start.js`: `ORIGIN` darf mehrere Adressen (kommagetrennt) enthalten; eigene Origin-Prüfung in `hooks.server.ts` ersetzt SvelteKits CSRF-Check.

## Kategorien

Optisch getrennte Bereiche (keine Filter): **Filme, Serien, Anime, Spiele**.

- In den Einstellungen ein-/ausblendbar (Setting `categories`, mindestens einer bleibt; `enabledCategories()` in `src/lib/server/settings.ts`). Ausgeblendet = weg aus Navigation, Suche, Dashboard; Direktaufruf leitet aufs Dashboard; Daten bleiben, aber kein Metadaten-Abgleich (Nachladen + nächtliche Aufgabe überspringen den Bereich). Gefahrenzone zeigt weiter alle Bereiche. Import fragt bei Titeln ausgeblendeter Bereiche nach (überspringen / trotzdem importieren / einblenden).

## Design

- Themes (Einstellungen → eigener persönlicher Bereich „Design“, `/settings/appearance`; Standard „System“ = folgt dem Gerät; „Dunkel“ ist das ursprüngliche Schema; dazu Hell, die bekannten Paletten Tokyo Night/Dracula/SynthWave '84 – im Reiter „Über“ genannt –, Cyberpunk (nach den Menüs des Spiels: fast alles in Korallenrot auf Schwarz mit rotem Schein, Cyan für Nebensächliches, Gelb nur als Tupfer; eckig, Knöpfe/Karten mit abgeschnittener Ecke, Versalien) sowie Retro 95 (erhabene Knöpfe/Fenster, vertiefte Felder, blaue Titelleiste), Terminal (grüner Leuchtschirm nach dem Pip-Boy aus Fallout 3: Leuchten, Bildzeilen, hellere Mitte) und „Brotkasten“/„Breadbin“ (Schlüssel `c64`: Hellblau auf Dunkelblau, Versalien, am PC mit Bildschirmrahmen) mit eckigen Kanten und eigener, lokal vorhandener Schrift). Namen der Themes vermeiden Marken (Spitznamen wie „Brotkasten“, Gattungsnamen wie „Cyberpunk“, „Terminal“). Vorlagen für solche Themes als Bild ansehen (Screenshot herunterladen und mit dem Lese-Werkzeug öffnen), nicht aus dem Gedächtnis bauen. Für solche Extras gibt es wenige Haken-Klassen, die in normalen Themes nichts bewirken: `ui-btn` an allem, was ein Knopf ist (Knopf-Konstanten in `SubmitButton.svelte`, Status-Kacheln, Folgen-Kacheln, Knöpfe der Detailseite, Theme-Kacheln), zusätzlich `ui-keep`, wenn der Knopf seine eigene Farbe behalten soll (aktueller Status, gesehene Folge); `ui-card` an Karten (`ui.card` in `src/lib/ui.ts`, Folgen-Karten, Hinweisboxen) und `data-chrome="header"`. **Neue Knöpfe und Karten bekommen diese Klassen**, sonst fallen sie in Retro 95 und Cyberpunk aus dem Rahmen; Hauptknöpfe tragen zusätzlich `ui-primary`. Damit bekannte Themes erkennbar sind, kann ein Theme neben der Grauskala Erkennungsfarben setzen: `--ui-heading` (Überschriften `h1`–`h3`, optional `--ui-heading-glow`), `--ui-primary`/`--ui-on-primary` (Hauptknopf), `--ui-link` (unterstrichene Textlinks) sowie die Statusfarben (`--color-emerald-*`, `--color-red-*`, `--color-amber-400`); ohne diese Angaben gilt die Grauskala. Echte Überschriften deshalb als `h1`–`h3` auszeichnen; runde Elemente (`rounded-full`) folgen der Variable `--round`. „System“ folgt dem Gerät: Werte von Dunkel, per `@media (prefers-color-scheme: light)` die von Hell – dieser Block ist ein Duplikat der hellen Werte und muss mit ihnen gepflegt werden. Jedes Theme muss bei neuen Oberflächenteilen mitgeprüft werden (Test: alle Themes durchschalten, Kontrast messen). Technik: Ein Theme tauscht die Grauskala aus, mit der die ganze Oberfläche gezeichnet ist – `[data-theme='…']`-Blöcke in `src/routes/layout.css` belegen `--color-zinc-*` neu (bei Bedarf auch `color-scheme`, einzelne Statusfarben, Eckenradien, Schrift); Liste in `src/lib/themes.ts`. **Neue Oberflächenteile deshalb nur über die `zinc`-Klassen einfärben, keine festen Grau-/Hex-Werte**; die Akzentfarben der vier Bereiche sind in jedem Theme dieselben Farben (`--accent-movies` usw. in `layout.css`; helle Themes nutzen nur eine dunklere Stufe für die Lesbarkeit) – in Komponenten per CSS verwenden (`style`), nicht als SVG-Attribut. Theme-Extras (z. B. dunkelblaue Kopfzeile bei Retro 95 über `data-chrome="header"`) stehen als wenige Regeln im Theme-Block, nie in den Seiten. Neues Theme = Eintrag in `themes.ts` + Block in `layout.css` + Name in `de.ts`/`en.ts`. Das Attribut wirkt auf jedem Element (Vorschau-Kacheln: `ThemePreview.svelte`). Welches Theme gilt, entscheidet `themeFor()` in `src/lib/server/theme.ts` und wird in `hooks.server.ts` direkt ins HTML geschrieben (kein Aufblitzen): angemeldet → persönliche Einstellung `theme` (wandert bei Mehrbenutzer zum Benutzer); abgemeldet (Login-Seite) → Cookie `hdtracker_theme` des Geräts (nur der Theme-Name, gesetzt beim Speichern und bei der Anmeldung) → sonst Theme der Installation (später Admin-Standard).
- Hover-Effekte (nur Maus) für alles Klickbare; Poster: Rahmen + Titel in Akzentfarbe, Bild leicht abgedunkelt, kein Zoom; kurze Übergänge (~100 ms), damit es direkt reagiert.
- Standard für neue Installationen: Oberfläche Englisch, Inhalte `en-US`, Region `US` (umstellbar in den Einstellungen).
- Navigation: Leiste unten (Handy), mit Icon + Label je Bereich.
- Breite: Kopfzeile + Poster-Seiten nutzen große Bildschirme (Utility `app-width` in `layout.css`: max. 140rem, am PC immer ~6,5 % Rand je Seite ≈ ¾ Poster; Poster-Raster `auto-fill`, am Handy 3 Spalten). Abschnitte der Bibliothek ohne Trennlinie. Detailseite `max-w-screen-xl`, Einstellungen `max-w-screen-md`; Dashboard und Leiste unten bleiben schmal.
- Gemeinsame Mittelachse am PC: Suchfeld (Kopfzeile als 3-Spalten-Raster mit gleich breiten Außenspalten), Inhalt und Leiste unten liegen mittig. Einstellungen ab xl: Inhalt mittig, Seitenleiste direkt links daneben.
- Suche in der Kopfzeile (bleibt beim Scrollen oben): am PC Suchfeld mit Icon des aktiven Bereichs (Klick öffnet Menü zum Umschalten; Taste `/` fokussiert), am Handy Lupe → Suchleiste gleitet von oben herein. Bereich = aktuelle Kategorie-Seite, sonst der zuletzt benutzte.
- Akzentfarbe je Bereich (neutraler Hintergrund): Filme rot, Serien blau, Anime pink, Spiele grün. Definiert in `src/lib/categories.ts`.
- Als App installierbar (PWA): `static/manifest.webmanifest`, Icons in `static/icons/` + `static/apple-touch-icon.png` (aus dem Logo erzeugt, dunkler Hintergrund mit Pink/Blau-Schimmer), Safari-Meta-Tags in `src/app.html`, `src/service-worker.ts` cacht nur App-Dateien (keine Seiten/Daten). Installation im Browser nur über HTTPS.
- Logo: Couch von vorne mit zwei Personen (links Schneidersitz/pink, rechts angewinkeltes Knie/blau). `src/lib/components/Logo.svelte`, auch als Favicon.
- Schriftzug „hdtracker“: Schrift Outfit (self-hosted via `@fontsource/outfit`, Tailwind-Klasse `font-brand`), „hd“ mit Verlauf pink→blau. `src/lib/components/Brand.svelte`.
- Poster-Raster für Suche und Bibliothek, aber nicht zu minimalistisch (kein reines Watcharr-Raster): Bibliothek braucht sichtbare Unterteilung in Abschnitte.

## Einstellungen (Aufbau)

- PC: Seitenleiste links, Handy: `/settings` zeigt eine gruppierte Liste, jeder Bereich hat „← Einstellungen“. Bereiche in `src/lib/settingsNav.ts` (neuer Bereich = eine Zeile + Seite unter `src/routes/settings/`). Überschrift „Einstellungen“ nur `sr-only`.
- **Persönlich** (je Benutzer): Allgemein (`/settings/general`: Oberflächensprache, Anime-Titel, Spoiler-Schutz, Auto-Status, Bereiche) · Design (`/appearance`: Farbschema) · Konto (`/account`: Benutzername, Passwort, andere Geräte) · Benachrichtigungen (`/notifications`, siehe eigener Abschnitt) · Daten (`/data`: Import, Export, Bibliothek leeren).
- **Verwaltung** (ganze Installation, Route-Gruppe `(admin)`): Server (`/server`: Übersicht, Inhaltssprache, Region, Verbindung/Reverse Proxy; die Übersicht zeigt wenige Prüfungen mit Stufe ok/Hinweis/Handlungsbedarf plus ein paar Fakten – Regeln in `evaluate()` in `src/lib/server/health.ts`, neue Prüfung = dort + Texte `settings.checks` + Link in `CHECK_LINKS`; bewusst knapp halten, keine Update-Prüfung, keine Live-Abfragen der Datenquellen) · Wartung (`/maintenance`) · später Benutzer. Geschützt über `isAdmin()`/`requireAdmin()` in `src/lib/server/auth.ts` (heute immer true, einziges Konto = Admin); Form-Actions und Endpunkte der Admin-Seiten rufen `requireAdmin` selbst auf.
- **Über** für alle, zuletzt.
- **Auswahl speichert sofort, ohne Knopf** (Wunsch des Users): Formulare, die nur aus Schaltern, Listen und Auswahlknöpfen bestehen, bekommen `use:autosave` (`src/lib/autosave.ts`, zusammen mit `use:enhance` + `FormFeedback.submit()`; **ohne „Gespeichert“-Meldung** – die Auswahl selbst ist Bestätigung genug, der User fand die Meldung störend; neben der Überschrift steht `FeedbackText` mit `forms.error(id)`, das nur einen Fehler zeigt) – so Allgemein, Design, Benachrichtigungen und der Anime-Schalter unter Server. Ein Knopf bleibt nur, wo getippt wird (Konto, Proxy-Adressen), wo mehrere Felder zusammengehören (Wartung) oder wo das Speichern viel auslöst (**Sprache der Inhalte und Region**: laden die ganze Bibliothek neu – bewusst mit Knopf). Neue Schalter-Formulare nach diesem Muster bauen.
- Knöpfe, die erst mit einer Eingabe Sinn ergeben, bleiben bis dahin ausgegraut: `SubmitButton` mit `when="changed"` (Formular weicht vom gespeicherten Stand ab – alle „Speichern“-Knöpfe) oder `when="filled"` (Pflichtfelder gültig ausgefüllt – Import, Passwort, Benutzername). Den gespeicherten Stand merkt sich der Knopf selbst; nach erfolgreichem Speichern meldet `FormFeedback.submit()` das dem Formular (Ereignis `saved`). Neue Formulare bekommen das passende `when`. Wartungsaufgaben: Weicht der Zeitplan vom Standard ab (`customSchedule`), erscheint neben „Wie oft“ ein kleiner Pfeil (Aktion `resetSchedule`, eigenes Mini-Formular, damit Enter weiter speichert) – bewusst kein weiterer Knopf, die Karten sind voll; „Standard wiederherstellen“ gibt es nur dort, nicht bei einfachen Schaltern und Auswahllisten. Die Untertitel der Bereiche in der Handy-Liste (`…Hint` in `de.ts`/`en.ts`) mitpflegen, wenn ein Bereich Inhalte bekommt oder verliert.

## Datenquellen

- TMDB: Filme, Serien inkl. Staffeln/Episoden, Watch Providers (Region DE). Attribution TMDB + JustWatch: im Reiter „Über“ (`/settings/about`, Version verlinkt auf die Release-Notes, GitHub, Issues, Lizenz) und JustWatch zusätzlich bei den Streaming-Angeboten der Detailseite.
- IGDB via Twitch OAuth: Spiele.
- AniList GraphQL: Anime.
- Folgentitel für Anime: AniList kennt keine Folgentitel → Titel, Text und Bild je Folge kommen aus TMDB, **immer auf Englisch** (`LANGUAGE` in `animeEpisodes.ts`), weil alles andere zu Anime (Titel, Beschreibung, Genres von AniList) auch englisch ist – der User wollte ausdrücklich keinen Sprach-Mix, die Beschreibung bleibt deshalb die von AniList (`providers/animeEpisodes.ts`, eingehängt in `loadAnimeWithTexts()` in `anilist.ts`). AniList bleibt Quelle für Titel, Beschreibung, Status, Folgenzahl, „ausgestrahlt“, Termine und Fortschritt. Welche TMDB-Staffel/Folgen zu einem AniList-Eintrag gehören, sagt die Community-Liste **anibridge-mappings** (MIT; `src/lib/server/animeMapping.ts`: ganze Liste höchstens einmal pro Woche von GitHub, entpackt mit `zlib.zstdDecompressSync`, nur `anilist → tmdb_show` in Tabelle `anime_tmdb_map` – direkt oder, wo die Liste nur die TVDB-Staffel nennt, über deren TMDB-Eintrag zusammengesetzt (`composeRanges()`, bringt ~250 Anime mehr); ändert sich die Lesart, `MAPPING_VERSION` erhöhen, dann wird die Liste sofort neu geholt und die Anime neu geladen; Abruf vor dem Anime-Paket in `refreshBatch()`; `prepareAnimeTitles()` holt sie beim Start einmalig, wenn es schon Anime gibt, und lädt diese neu – so kommen die Titel nach einem Update sofort). Ob und wann eine Folge läuft, bestimmt allein AniList: ein TMDB-Datum wird nur für schon ausgestrahlte Folgen übernommen. Die Liste ist nicht verlässlich (mehrere/falsche Ziele), deshalb **Prüfung jeder Zuordnung**: Die für Folge 1 genannte TMDB-Folge muss existieren und ihr Sendetag zum AniList-Starttag passen (± 2 Tage); verschachtelte Bereiche (`|n`, Komma) werden nicht unterstützt. Im Zweifel ohne: kein Treffer, Prüfung nicht bestanden, TMDB nicht erreichbar oder Schalter aus (Setting `animeEpisodeTitles`, Einstellungen → Server, Standard an; umschalten lädt die Anime neu) → Anime wie von AniList, nie ein Fehler. TMDB wird mit `getTvSeasons()` gefragt: **eine** Abfrage je Anime, nur die von der Liste genannten Staffeln (`season/N`) plus die Streaming-Angebote der Staffel(n), die für Folge 1 genannt sind (`season/N/watch/providers`; beides lässt sich an `/tv/{id}` anhängen, höchstens 20 Teile je Abfrage – nur Dauerläufer mit > 18 Staffeln brauchen zwei). Die Abfrage startet gleichzeitig mit der an AniList (`warmUpAnimeTexts()`), weil sie nur von der Liste abhängt – gemessen öffnet ein Anime außerhalb der Bibliothek damit so schnell wie ohne Folgentitel (~0,3–0,5 s; mit erstmaligem Wikidata-Direktlink ~1 s, wie bei Serien). **Streaming bei Anime:** Mit geprüfter Zuordnung und Angeboten in der Region ersetzen die JustWatch-Angebote der TMDB-Staffel (staffelgenau – Staffeln liegen oft bei verschiedenen Diensten; Direktlinks über Wikidata wie bei Serien, 30 Tage gespeichert) die AniList-Links; ohne Zuordnung oder ohne Angebote bleiben die AniList-Links als Rückfall. Ist ein Anime nur ein Teil einer TMDB-Staffel, gelten die Angebote der ganzen Staffel (feiner kennt TMDB es nicht). Quelle ist im Reiter „Über“, in der README und im Wiki genannt und verlinkt.
- Wikidata: Direktlinks zu Titeln bei Streaming-Diensten (Detailseite Filme/Serien); im Reiter „Über“ mit aufgeführt.

## Benachrichtigungen

- Persönlicher Bereich `/settings/notifications` mit **zwei Karten**: „Neuerscheinungen“ (_was und wann_: Melden Aus/Einzeln/Gesammelt, „Ab wann“ – nur sichtbar, solange Meldungen an sind) und **„Ziele“** (_wohin_). Standard aus.
- **Ziele = eine Liste für alles** (`src/lib/components/TargetList.svelte`, Daten aus `listTargets()` in `src/lib/server/targets.ts`): Geräte (Push direkt aus der App), Pushover, ntfy, Webhook. Je Ziel eine Zeile mit Symbol, Name, Stand („zuletzt erreicht“/letzter Fehler in Rot) und **Schalter** (speichert sofort; aus = bleibt mit allen Angaben stehen). Antippen klappt auf: Name, Felder der Art, „Speichern“, **„Test“ nur für dieses Ziel** (bewusst kein gemeinsamer Test-Knopf: er ließe alle Geräte mitklingeln; auch ein ausgeschaltetes Ziel lässt sich testen), „Entfernen“. „Ziel hinzufügen“ fragt die Art; „Dieses Gerät“ ist ausgegraut mit einem erklärenden Satz, wenn es hier nicht geht (kein HTTPS, blockiert, iPhone ohne installierte App), und fehlt, wenn das Gerät schon in der Liste steht. Mehrere Ziele einer Art sind erlaubt (Deckel 10 je Benutzer). Sind die Meldungen insgesamt aus, steht ein gelber Satz über der Liste – die Liste wird **nicht** abgedunkelt (abgedunkelt, aber bedienbar, fand der User widersprüchlich). Technisch bleiben Geräte in `push_subscriptions` (Adresse + Schlüssel des Browsers), die übrigen Ziele in `notification_channels` (`kind`, `name`, `enabled`, `config` als JSON, `last_ok_at`, `last_error`); `deliver(userId, notice, only?)` in `targets.ts` schickt an alle eingeschalteten oder an genau eines. Geheimnisse (Pushover-Token/-Schlüssel, ntfy-Zugangsschlüssel, Webhook-Kopfzeile) gehen **nie** an die Seite zurück (`publicChannel()`), leeres Feld = behalten.
- **Pushover** (`src/lib/server/channels/pushover.ts`): eigener App-Token des Nutzers + Benutzerschlüssel (kein fester Token im Code – bewusst), beim Speichern bei Pushover geprüft (`users/validate.json`); die Antwort nennt die Geräte des Kontos (vom User am echten Konto bestätigt) – sie stehen unter dem optionalen Feld „Nur an diese Geräte“ zum An-/Abwählen (`DeviceFilter.svelte`). Der Filter ist genau Pushovers Parameter `device` (leer = alle, mehrere mit Komma; unbekannter Name = Pushover schickt an alle). Nachricht mit Titel, Text, Link „In hdtracker öffnen“ und der Filmkarte/Poster-Reihe als Anhang (Datei, gebaut mit `composePosters()`). **Grenzen von Pushover:** Antippen der Benachrichtigung öffnet immer die Pushover-App; das Bild kann kein Link sein. Pushover liest Titel, Text und Bild mit (steht im Wiki; am 06.10.2026 gegen Pushovers eigene Unterlagen geprüft: Klartext auf deren Servern bis zur Zustellung, höchstens 21 Tage, Bilder 3 Tage; für den Weg über Apple/Google verschlüsselt Pushover selbst). Pushover bietet Ende-zu-Ende-Verschlüsselung mit eigenem Schlüssel an (`encrypted=1`, nur Titel/Text/Link, AES-256-CBC + HMAC) – **nicht eingebaut**, mögliche Erweiterung.
- **ntfy** (`src/lib/server/channels/ntfy.ts`; gebaut als Option für später – der User nutzt vorerst Pushover): Server (Standard `https://ntfy.sh`), Thema, optional Zugangsschlüssel und Icon-Adresse, Schalter „Bild anhängen“. Beim Speichern wird nichts gesendet (wie beim Webhook, dafür ist „Test“ da). Versand: `PUT {server}/{thema}`, Titel/Text als Kopfzeilen in RFC-2047-Verpackung (Umlaute, Emoji, Zeilenumbrüche), Link als `Click`; **das Bild wird als Datei hochgeladen** (kommt deshalb auch an, wenn das Handy hdtracker nicht erreicht – anders als `{{image}}` im Webhook), **das Icon ist nur eine Adresse**, die das Handy selbst lädt (leer = `/icons/icon-192.png` dieser Installation; wer von außen nicht erreichbar ist, trägt eine öffentliche Adresse ein, das Wiki nennt die im GitHub-Repo). Nimmt der Server keine Dateien (Antwort 400/413, bei eigenen Servern Standard), geht die Nachricht ohne Bild noch einmal raus. Geprüft gegen echte ntfy-Container (mit/ohne Anhänge, geschützt mit Schlüssel) und ntfy.sh; **wie es in der ntfy-App aussieht, hat niemand am Handy gesehen**. Für Mehrbenutzer gilt dieselbe Einschränkung wie beim Webhook (frei wählbare Server-Adresse). Datenschutz (laut ntfy-Unterlagen, steht im Wiki): keine Ende-zu-Ende-Verschlüsselung; ntfy.sh hält Nachrichten 12 h, Bilder 3 h, und veröffentlicht laut ntfy alle Nachrichten zusätzlich bei Googles Firebase („content may be transmitted through Google's FCM infrastructure“ – so zitieren, nicht zuspitzen); ein eigener Server nutzt Firebase nicht und schickt nur mit gesetztem `upstream-base-url` (iPhone) Nachrichten-ID + Prüfsumme des Themas an ntfy.sh.
- **Webhook** (`src/lib/server/channels/webhook.ts`): Adresse (http/https), Inhalt mit Platzhaltern `{{title}}`, `{{message}}`, `{{url}}`, `{{image}}`, `{{count}}`, `{{test}}` (JSON-Vorlagen: Werte werden für JSON maskiert, Content-Type folgt), optionale Kopfzeile „Name: Wert“; `POST`, 10 s, **keine Weiterleitungen**. Private Adressen sind erlaubt (ntfy/Home Assistant im eigenen Netz sind der Zweck) – **mit Mehrbenutzer müssen Webhooks den Admins vorbehalten oder eingeschränkt werden**, sonst kann jeder Benutzer den Server ins eigene Netz anfragen lassen (steht auch im Kopf der Datei). Vorlagen im Wiki (`Notifications`) nur für Dienste, die gegen einen echten Container geprüft wurden (Gotify, Apprise API – mit und ohne dort gespeicherte Konfiguration, Bild über `"attach": "{{image}}"`). **Apprise wird bewusst nicht eingebaut** (Python-Baukasten: bräuchte Python im Image oder ohnehin einen zweiten Container; Apprise-Adressen zum Eintippen sind für Laien kryptisch) – wer es nutzt, hängt die Apprise API über den Webhook an.
- Geräte (Web Push): braucht HTTPS; iPhone/iPad nur als installierte App, dort zeigt das System immer nur das App-Icon (weder Poster noch Mashup).
- Versand (`src/lib/server/push.ts`): Baustein `web-push` nur für Verschlüsselung/Signatur (`generateRequestDetails()`), **gesendet wird mit unserem `fetch`** (Tests ohne Netz, Browser-Test-Sperre greifen). Die Adresse eines Geräts kommt vom Browser → **feste Liste erlaubter Push-Dienste** (`PUSH_HOSTS`: Google FCM, Mozilla, Apple, Microsoft; nur https), sonst könnte der Server zu beliebigen Adressen geschickt werden. Jede Nachricht geht mit **`Urgency: high`** raus: Mit dem Standard („normal“) stellt Android sie nur sofort zu, wenn die App (bzw. Chrome) gerade offen ist – beim User kam die 6-Uhr-Meldung trotz benutztem Handy erst beim Öffnen der App, Pushover dagegen pünktlich; mit „high“ kam sie bei geschlossener App zur vollen Stunde (vom User am Pixel bestätigt, 06.10.2026). Antwort 404/410 = Gerät gibt es nicht mehr → Eintrag löschen. Ersetzt ein Browser sein Abo (neu abonniert in `addThisDevice()` oder von sich aus, `pushsubscriptionchange` im Service Worker), schickt er die alte Adresse als `replaces` mit: `addDevice()` schreibt dann den vorhandenen Eintrag um (Name und Schalter bleiben) statt einen zweiten anzulegen – sonst stünde das Gerät doppelt in der Liste, einmal davon tot. Nur eigene Einträge, die Adresse kommt vom Browser. VAPID-Schlüssel der Installation liegen in `settings` (beim ersten Gebrauch erzeugt, privater Teil wird nie ausgeliefert).
- Was gemeldet wird (`src/lib/server/notifications.ts`): genau das, was am Tag im Dashboard unter „Kürzlich erschienen“ steht – die Regel steht einmal in `trackedEvents()` (`dashboard.ts`), die Wortwahl einmal in `eventLabel()` (`src/lib/eventLabel.ts`); beides nutzen Dashboard und Meldungen. Wir kennen nur den Tag, keine Uhrzeit: Aufgabe `notifications` (stündlich, **nicht abschaltbar** – ob gemeldet wird, entscheidet allein die Einstellung des Benutzers; ohne eingeschaltete Meldungen liest ein Lauf drei Einstellungen und endet) sendet je Benutzer ab seiner gewählten Stunde; Verpasstes wird 2 Tage nachgeholt; Merker `notifications_sent` (eigene Tabelle, weil `releases` bei jeder Aktualisierung neu geschrieben wird); beim Einschalten zählt erst ab heute (`notifyFrom`); ohne Gerät wird nichts aufgespart. Form `single` (eine Nachricht je Titel, öffnet den Titel) oder `digest` (eine am Tag, öffnet das Dashboard). Einzelne Titel stumm: `library_items.notify`, Glocke auf der Detailseite (nur sichtbar, solange Meldungen an sind). Der Test eines Ziels schickt ein echtes Beispiel aus dem Dashboard (`sampleMessage()`, markiert mit „Test ·“). „Niemand da“ heißt: kein eingeschaltetes Ziel (`hasEnabledTarget()`); gemeldet gilt, sobald ein Ziel geklappt hat.
- Bilder einer Nachricht: klein (`icon`) **immer der Kalender** in den Logo-Farben (`static/icons/notify.png`, aus dem Lucide-Icon gerendert); groß (`image`, sichtbar beim Aufklappen auf Android und in Chrome am PC) bei einem Titel eine **„Filmkarte“**: das ganze Poster mittig vor einer weichgezeichneten, dunklen Vergrößerung seiner selbst (eine frühere Fassung setzte das Banner des Titels dahinter – Poster und Banner passten oft nicht zusammen, der User wollte es so stimmiger; ein Titel ohne Poster bekommt ersatzweise sein Banner unverändert); bei der Sammelnachricht ab zwei Postern eine Reihe aus bis zu vier. Wünsche des Users dahinter: Poster nicht klein **und** groß (doppelt), aber das Poster muss zu sehen sein (am Banner allein erkennt man den Titel oft nicht). Das Gerät lädt Bilder ohne Anmeldung → **signierte Adressen** (`signedImagePath()`/`isSignedImage()`, `signedCollagePath()`/`readCollageAddress()` in `images.ts`, Ausnahme in `hooks.server.ts`): öffnen genau dieses eine Bild. Zusammengesetzt wird in `src/lib/server/collage.ts` mit **`sharp`** (libvips; Layouts `wide` = Reihe, `banner` = Filmkarte aus dem Poster), ausgeliefert über `/img/collage` – **nichts auf Vorrat, nichts auf der Platte**: entsteht erst beim Abruf, 10 Minuten im Arbeitsspeicher, Adresse läuft nach 7 Tagen ab. Warum `sharp` (natives Modul, deshalb unter `dependencies` wie `better-sqlite3`; Docker-Stufe `deps` holt das Binary je Architektur, ~18 MB): Es rechnet außerhalb des Server-Fadens und liest Bilder verkleinert ein. Gemessen (30 Bilder, Alpine wie im Image): 0,05–0,1 s je Bild, Server antwortet durchgehend (einmalig ~30 ms beim ersten Laden von `sharp`, sonst < 10 ms), +4–7 MB Speicher. Zwei Vorgänger wurden verworfen: reines JavaScript (`jpeg-js`/`pngjs`) hielt den Server 0,25–0,3 s je Bild an; dasselbe in einem Hilfsprozess hielt 120–190 MB. **Lässt sich `sharp` nicht laden (z. B. fehlendes Binary), gibt es kein großes Bild, die App läuft weiter.** Das Laden selbst hält den Server einmalig ~30 ms an und belegt danach ~25 MB – deshalb weder für alle beim Start noch irgendwann mitten im Betrieb: `preparePictures()` wird gerufen, wenn Meldungen in Gebrauch sind (beim Start über `prepareNotificationPictures()`, und beim Einschalten in `savePrefs()`); wer keine Meldungen nutzt, zahlt nichts. Das erste Bild lädt als Sicherheitsnetz nach. Sparsam eingestellt (`cache(false)`, `concurrency(1)`). Eigenheit: `sharp` wendet Schritte einer Kette in fester Reihenfolge an (Abdunkeln nach dem Zusammensetzen) – der Hintergrund wird deshalb erst fertig gerechnet, dann kommt das Poster in einem zweiten Schritt darauf. Auf glibc-Systemen (lokale Entwicklung) wächst der Speicher stärker als auf Alpine; `MALLOC_ARENA_MAX=2` hilft dort. Kein Text im Bild (der Server kann ohne weiteren Baustein keine Schrift zeichnen).
- Android: `badge` muss eine weiße Form auf transparent sein (`static/icons/badge-96.png`, aus dem Logo; ein buntes Icon wird zum weißen Kasten), ohne `icon` malt Chrome den ersten Buchstaben der Adresse. Als Absender steht „hdtracker“ nur, wenn die App wirklich installiert ist (sonst „Chrome“).
- Mehrbenutzer: Geräte und Merker tragen `user_id`, alle Aktionen filtern auf den angemeldeten Benutzer; Form/Uhrzeit sind persönliche Einstellungen, gelesen an einer Stelle (`prefsFor()`). Echte Zustellung lässt sich nicht automatisch testen (Test-Browser hat keinen Push-Dienst) – das prüft der User am Gerät.

## Config

- Nur Secrets in `.env`: `SECRET`, `TMDB_API_TOKEN` (Read Access Token, als Bearer-Header), `IGDB_CLIENT_ID`, `IGDB_CLIENT_SECRET`, `TZ`, plus `ORIGIN` (Pflicht: exakte Adresse, über die die App aufgerufen wird; ohne ORIGIN nimmt adapter-node https an und Formulare scheitern mit 403). `.env` ist in `.gitignore`.
- Reverse Proxy (Einstellungen → Server → „Verbindung“; bewusst in der Oberfläche statt in der `.env`, weil die Einstellung den Zugang nicht blockieren kann – anders als `ORIGIN`): Der weitergereichten Besucher-Adresse (`X-Forwarded-For`) wird **nur geglaubt, wenn sich der Proxy ausgewiesen hat** – über seine Adresse (Setting `trustedProxies`, Adressen/Bereiche, ein Klick „Bestätigen“) oder über einen Schlüssel (Setting `proxyKey`, Kopfzeile `X-Hdtracker-Proxy-Key`), sonst gilt die Adresse der Verbindung; ein direkter Besucher kann nichts vortäuschen (`src/lib/server/proxy.ts`). Der Schlüssel ist für Aufbauten, in denen Docker alle Verbindungen selbst weiterreicht und jede vom Gateway kommt (rootless Docker – so läuft die Test-VM –, Zugriff vom Host, IPv6): `defaultGateway()` erkennt das, die Karte bietet dann den Schlüssel statt „Bestätigen“ an. Adresse immer über `clientAddress(event)`/`connectionOf(event)` (`auth.ts`) holen, nie `getClientAddress()`; `ADDRESS_HEADER`/`XFF_DEPTH` von adapter-node werden nicht benutzt. Die Zeilen für die Proxys (`src/lib/proxySnippets.ts`, auch im Wiki) sind gegen echte Container geprüft (Caddy, nginx, Traefik, Nginx Proxy Manager – dort wirkt nur eine Custom Location, nicht „Advanced“); neue nur nach solchem Test aufnehmen. Login-Sperre je Adresse: 5 Fehlversuche → 1, dann 5, dann 15 Minuten (im Speicher, nach einem Tag vergessen). Der Schlüssel wird in der Karte verdeckt gezeigt (Auge blendet ein, „Kopieren“ nimmt immer die echte Zeile). Gestaltung der Karte: Statusmarke in Farbe, Zeile „Erkannt als“ (= die Adresse, für die gezählt wird), Bezeichnung-Wert-Liste, höchstens ein Knopf, Details zugeklappt – wenig Text.
- Alle anderen Einstellungen (Region, Sprache, …) liegen in der DB (Tabelle `settings`), editierbar über die Settings-Seite.
- Persistente Daten unter `DATA_DIR` (Container: `/data`, lokal: `./data`).

Absätze und Listenpunkte über ~50 Wörter und Tabellenzellen in Absatzlänge auflösen. Beim Umbenennen von Überschriften die Sprungmarken mitziehen (auch im App-Code: `WIKI` in `src/routes/settings/notifications/+page.svelte`).
- Ändert sich etwas an Installation, `.env`, Update, Backup, Import oder Rettungswegen: Wiki-Seite mit anpassen und pushen (Wiki-Commits wie Code-Commits erst nach Okay).
- Datenschutz: **Aussagen darüber, wer was lesen kann, nur nach Prüfung am Originaltext des jeweiligen Dienstes** (Datenschutzseite, API-Doku; den Text selbst lesen, nicht eine Zusammenfassung) und mit Link darauf – der User will das sehr genau und unmissverständlich. Im Wiki getrennt halten: „was hdtracker sendet“ (wissen wir aus dem Code), „was der Dienst selbst angibt“ (mit Link und Datum, nicht nachprüfbar) und „eigener Test“. Die ausführliche Fassung steht nur auf „Privacy and security“, die Seite „Notifications“ fasst in je einem Satz zusammen und verweist dorthin. Die Wiki-Seite „Privacy and security“ listet **jede** Verbindung nach außen (Server: TMDB, Twitch/IGDB, AniList, Wikidata und deren Bildserver; Browser: nichts – er spricht nur mit hdtracker) und wie Daten gespeichert sind. Kommt eine Verbindung dazu oder ändert sich etwas daran (neuer Dienst, neue Bildquelle, Pushover, Cookies/Speicherung, Login-Schutz), die Seite mit anpassen. Keine Telemetrie, keine Update-Prüfung, keine fremden Skripte/Schriften einbauen.
- Bilder: Der Browser lädt Bilder nie direkt von den Diensten. Jede Bild-Adresse geht in der Oberfläche durch `img()` (`src/lib/images.ts`) → `/img?u=…` (`src/routes/img/+server.ts`, nur angemeldet); der Server holt das Bild (`src/lib/server/images.ts`), prüft per Dateianfang, dass es ein Bild ist, und speichert es unter `DATA_DIR/images`. Fristen je Quelle in der Tabelle `SOURCES` dort (TMDB: max. 6 Monate laut Nutzungsbedingungen; IGDB/AniList ohne Angabe → gleich behandelt): Auffrischen 1 Monat vor der Frist (bei kurzer Frist 7 Tage davor; AniList alle 7 Tage, weil dort eine Adresse ein anderes Bild bekommen kann), schlägt das fehl, gilt die alte Kopie bis 5 Tage vor der Frist. Neues Poster bei TMDB/IGDB = neue Adresse → kommt mit der nächsten Metadaten-Aktualisierung. `refreshItem()` hält die Poster der Bibliothek vorrätig. Die nicht abschaltbare Aufgabe `images` („Bilder aufräumen“, `required` in `scheduler.ts`) löscht, was 30 Tage nicht angefragt wurde oder über der Frist liegt. Erlaubte Quellen stehen als feste Liste in `src/lib/images.ts` (neue Bildquelle = dort und in `SOURCES` eintragen, nie beliebige Adressen zulassen). Wartungsseite zeigt belegten Speicher (Bilder, Datenbank, Backups) und nach einem Lauf den freigegebenen (`tasks.last_freed_bytes`). In der DB bleiben die Original-Adressen. Die Kopfzeile CSP (`vite.config.ts`, `csp.directives`) erlaubt dem Browser nur Inhalte und Skripte vom eigenen Server (`default-src 'self'`, Bilder `'self' data:`, kein Einbetten über `frame-ancestors 'none'`; `style-src` braucht `'unsafe-inline'` für `style="color: …"`) und verhindert so auch direkte Bilder; `hooks.server.ts` ergänzt bei jeder Antwort `X-Frame-Options`, `X-Content-Type-Options` und `Referrer-Policy`. Neue Oberflächenteile dürfen deshalb nichts von fremden Adressen laden und keine eingebetteten Skripte (`<script>` in `app.html`, `onclick="…"`-Attribute) nutzen.
- Vorladen: Für jeden Bibliothekstitel hält `refreshItem()` (`src/lib/server/releases.ts`) alles vor, was die Detailseite zeigt – Details und Folgenliste als JSON in der Tabelle `item_details` (`src/lib/server/itemDetails.ts`), dazu Poster, Banner und Anbieter-Logos im Bild-Speicher (≈ 0,2 MB je Titel). Folgenbilder und die Poster der „Ähnlichen Titel“ werden bewusst nicht vorgeladen (viel Platz, liegen weiter unten auf der Seite) – sie kommen beim Ansehen und bleiben dann gespeichert. Läuft direkt nach Hinzufügen/Import (Warteschlange), jede Nacht (Aufgabe `metadata`, ohne ausgeblendete Bereiche; Rhythmus je Titel siehe „Sparsam abfragen“) und nach Änderung von Inhaltssprache/Region. Regel „Bibliothek = vorgehalten, sonst live“ steht an einer Stelle: `detailsFor()` in `itemDetails.ts` (Detailseite + Folgen-Aktionen); Stand älter als 1 h wird gezeigt und im Hintergrund aufgefrischt (`refreshSoon()`). „Ausgestrahlt“ wird beim Lesen anhand des Datums nachgezogen. Ausgeblendete Bereiche: gespeicherte Details werden beim nächtlichen Lauf gelöscht und nach dem Einblenden neu geladen. Anime: alles (Folgen, Termine, Detailseite) kommt aus **einer** AniList-Abfrage (`ANIME_QUERY`/`fetchAnime()` in `providers/anilist.ts`, für einen oder bis zu 25 Titel; AniList erlaubt nur ~30 Abfragen/Minute) – neue Felder dort ergänzen, keine zweite Abfrage je Titel einführen. „Jetzt ausführen“ wartet höchstens 10 s, lange Läufe laufen im Hintergrund weiter.
- Sparsam abfragen (die Dienste bitten darum): Je Titel genau **eine** Abfrage pro Dienst – `loadMovie()`/`loadTv()` (`providers/tmdb.ts`; Serien holen Detailseite + Staffeln 0–16 in einer Abfrage, nur längere brauchen weitere), `loadGame()` (`igdb.ts`), `loadAnime()` (`anilist.ts`); Termine, Folgen und Detailseite werden daraus abgeleitet. Neue Felder dort ergänzen statt eine zweite Abfrage einzuführen. Im Hintergrund (Warteschlange nach Hinzufügen/Import, nächtliche Aufgabe) werden Anime und Spiele **im Paket** geholt: `preloadAnime()` (25 je Abfrage) und `preloadGames()` (50 je Abfrage) legen die Antworten in den Zwischenspeicher, `refreshItem()` arbeitet danach ohne eigene Abfrage (`refreshBatch()` in `releases.ts`; scheitert ein Paket, fragt jeder Titel wie früher einzeln; TMDB kennt keine Paket-Abfrage). Wikidata (Direktlinks zu Streaming-Diensten, User-Agent mit Version + Kontakt): Antwort 30 Tage in Tabelle `wikidata_links`, nur bei Titeln mit Streaming-Angebot. Im Hintergrund **eine Abfrage für das ganze Paket** über den Abfragedienst (`preloadStreamingLinks()`, SPARQL an `query.wikidata.org`, bis 100 Titel, nur die gesuchten Kennungen – die Alternative `wbgetentities` schickt je Titel den ganzen Eintrag mit): `preloadTmdb()` lädt dafür erst die Filme/Serien eines Pakets (je eine TMDB-Abfrage, landen im Zwischenspeicher) und fragt dann die Links aller Titel mit Angebot auf einmal; `preloadAnimeTexts()` macht dasselbe für Anime und bündelt außerdem Staffeln derselben Serie zu **einer** TMDB-Abfrage je Serie (`preloadTvSeasons()`). Scheitert das Paket, fragt jeder Titel einzeln (`Special:EntityData`, auch beim Öffnen einer einzelnen Seite). Gemessen (67 Titel neu laden): Wikidata 3 statt 45 Abfragen, 11 s statt 48 s, gespeicherte Links und Streaming-Blöcke identisch. Rhythmus der nächtlichen Aufgabe (`isDue()` in `releases.ts`): Geplant/Schaue/Pausiert und gesehene, noch laufende **Serien** jede Nacht; gesehene Filme und Anime, gesehene beendete/abgesetzte Serien (`ended` in den gespeicherten Details, `endedShowIds()`) sowie durchgespielte Spiele einmal pro Woche; Abgebrochenes einmal im Monat (damit nichts Gespeichertes älter wird als die 6 Monate, die TMDB erlaubt). „Jetzt ausführen“ folgt derselben Regel; beim Öffnen einer Detailseite wird ein älterer Stand ohnehin im Hintergrund aufgefrischt. Kennt die Quelle einen Titel nicht mehr (Antwort 404), ist das kein Fehler: `refreshOrMarkMissing()` setzt `library_items.source_missing_since`, das Gespeicherte bleibt, nachgefragt wird nur noch einmal im Monat; wird der Titel wieder gefunden, verschwindet die Markierung. Sichtbar als Hinweis auf der Detailseite und als Zeile in der Server-Übersicht. Hintergrund-Abfragen laufen nacheinander mit Pause je Dienst (`PAUSE_MS` in `providers/types.ts`: TMDB 0,1 s, IGDB 0,3 s, AniList 3 s, Wikidata 1 s) und warten bei „zu viele Anfragen“.
- Export (`src/lib/server/export/yamtrack.ts`, Download unter `/settings/data/export`): schreibt die ganze Bibliothek als CSV im Format von Yamtracks eigenem Export (gleiche Spalten/Reihenfolge wie die Vorlage in `data/yamtrack_*.csv`; Serien als `tv` + `season` + `episode`-Zeilen), sodass Yamtrack und der eigene Import sie lesen. **Rein lokal – ein Export fragt nie eine API.** Dafür wird die MyAnimeList-Kennung jedes Anime (AniList-Feld `idMal`) beim normalen Laden mitgespeichert (`library_items.mal_id`, `SearchResult.malId`); Anime ohne Kennung fehlen in der Datei, die Daten-Seite nennt ihre Zahl. Getestet gegen echtes Yamtrack: alle Zeilen und Status kommen an; `created_at`, Film-/Staffel-`progress` und Staffelbild setzt Yamtrack selbst. Bei Änderungen am Import das Gegenstück im Export mitdenken (Hin-und-zurück-Test: Export → leere Instanz → gleiche Bibliothek).
- Passwort vergessen: `reset-password.js` im Projektstamm (ins Image kopiert) setzt ein Übergangspasswort und meldet alle Geräte ab; schreibt dasselbe Hash-Format wie `hashPassword()` in `auth.ts` – beide zusammen ändern.

## Changelog & Releases

- `CHANGELOG.md` (Englisch, Emoji-Stil): Jede für Nutzer sichtbare Änderung sofort unter `## Upcoming release` eintragen (die Überschrift gibt es nur, solange es solche Änderungen gibt: bei der ersten Änderung nach einem Release oben anlegen, direkt nach einem Release steht sie nicht da), in `### ✨ New` / `### 🔧 Improved` / `### 🐛 Fixed` / `### 🗑️ Removed`. Aus Nutzersicht formulieren („Search is now in the header“), nicht technisch. Rein interne Änderungen (CI, Aufräumen, Tests) und Änderungen an README/Wiki gehören nicht hinein – nur, was sich in der App selbst für Nutzer ändert (z. B. ein neuer Link in der App, nicht der Umbau der Doku).
- Versionen bis 1.0: neue Funktionen → `0.X.0`, nur Fehlerbehebungen → `0.X.Y`.
- Release: Changelog-Text vorher dem User zeigen. Dann `## Upcoming release` → `## X.Y.Z – JJJJ-MM-TT` (leere Unterabschnitte weg, Wichtigstes zuerst, ein kurzer Einleitungssatz, am Ende `### ⬆️ Updating` mit dem, was Nutzer beim Update tun müssen) – kein neuer leerer `## Upcoming release`-Abschnitt; Version in `package.json` (`npm version X.Y.Z --no-git-tag-version`); Commit, Tag `vX.Y.Z`, Push.
- Die GitHub Action baut das Image und stellt danach den Release-Text in ihre Zusammenfassung: Abschnitt der Version aus `CHANGELOG.md` + Image-Zeile + „Full Changelog“-Link zum vorigen Tag (ohne Abschnitt schlägt sie fehl). **Das GitHub-Release legt der User selbst an**, damit er als Autor erscheint – bewusst ohne Personal Access Token (Sicherheit). Nach dem Tag-Push den fertigen Text im Chat mitgeben.

## Befehle

- `npm run dev` – Dev-Server (http://localhost:5173)
- `npm run check` – Typprüfung
- `npm test` – automatische Tests (vitest). Jede Testdatei bekommt eine leere, echte Datenbank in einem Temp-Ordner und **kein Netz** (`src/tests/setup.ts`); API-Antworten gibt ein Test mit `mockFetch()` vor, Titel legt `addItem()` an (`src/tests/helpers.ts`). Tests liegen neben dem Code (`*.test.ts`). **Neue oder geänderte Regel-Logik (Status, Termine, Rhythmus, Import/Export, Login, erlaubte Quellen) bekommt einen Test.**
- `npm run test:e2e` – Browser-Tests der Hauptabläufe (Playwright, Ordner `e2e/`, ~40 s): bauen die App, starten sie mit leerem Datenordner auf Port 4173 und klicken Einrichtung, Anmeldung, Film/Serie, Folgen, Dashboard, Einstellungen, Export/Import und Schutz durch. **Keine echten Datenquellen:** `e2e/fake-apis.mjs` wird in den Server-Prozess vorgeschaltet und beantwortet alle Anfragen nach außen mit erfundenen Titeln aus `e2e/fixtures.mjs` (Termine relativ zu heute); alles andere wird blockiert und als „FAKE-APIS blocked“ gemeldet. Die App selbst bekommt keinen Test-Modus. Die Tests bauen aufeinander auf (Nummern im Dateinamen, ein Worker), suchen Knöpfe über Rolle und Beschriftung (englische Oberfläche, dunkles Theme) und warten auf sichtbare Zustände statt fester Pausen. **Neuer oder geänderter Hauptablauf → Browser-Test ergänzen/anpassen**; liest ein Provider neue Felder, die Testdaten in `fixtures.mjs` mitpflegen. Bei Zufallsfehlern nachschärfen, keine Wiederholungen einschalten.
- `npm run lint` – Formatprüfung (Prettier). GitHub prüft bei jedem Push auf `main` und vor jedem Release: `check`, `lint`, `test` und in einem zweiten Job die Browser-Tests (`.github/workflows/check.yml`).
- `npm run build` / `npm start` – Production-Build starten
- `npm run db:generate` – nach Schema-Änderung neue Migration in `drizzle/` erzeugen (mit committen!)
- `docker compose up -d` – veröffentlichtes Image von GHCR starten (wie auf einem Server)
- `docker compose -f docker-compose.yml -f docker-compose.build.yml up -d --build` – Image lokal aus dem Quellcode bauen und starten
- Release: siehe „Changelog & Releases“; Tag `vX.Y.Z` pushen → GitHub Action baut Multi-Arch-Image nach GHCR; die Release-Seite legt der User mit dem vorbereiteten Text an
